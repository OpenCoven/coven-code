# Coven Code as a research-based coding harness

Research brief by Sage, November 26, 2026. Repository snapshot [21e3ac83](https://github.com/OpenCoven/coven-code/commit/21e3ac83e7382c36abae14c6932b2d044adc29a0). This is a source and evidence review. It establishes comparative engineering maturity by dimension. It includes no new live-model runs, installed-client qualification, or head-to-head scores.

## Assessment

Coven Code has a strong foundation for a local coding harness. Its clearest strengths are bounded execution, machine-readable failure states, explicit continuation semantics, and tests that exercise real engine processes. Its largest gap is evidence about how often the whole system produces a correct, reviewable change under realistic conditions. The inspected tree has protocol, lifecycle, security-policy, and terminal regressions. I found no versioned, repeated live-model task suite with independent outcome grading and published run receipts. Confidence in the design is therefore higher than confidence in its relative task performance.

There are two useful meanings of harness engineering here. The **runtime harness** controls the model loop, tools, authority, state, and user intervention. The **repository as a harness** gives any coding agent a legible map, runnable checks, isolated work, and trustworthy feedback. Coven Code has meaningful investment in both. A third layer, the **evaluation harness**, should measure how changes to either affect actual delivery. OpenAI's internal product case study illustrates the repository layer with navigable documentation, mechanically enforced constraints, and agent-accessible runtime feedback. Its evidence comes from one deployment context. [OpenAI, Harness engineering](https://openai.com/index/harness-engineering/)

## What the research changes

**Tool design is part of the experiment.** SWE-agent found that changing the interface available to a model affected navigation, editing and test execution on its evaluation tasks. This supports testing tool changes with a matched model and budget. Its historical scores do not establish a current baseline for Coven Code. Start with one narrow hypothesis, such as whether bounded test output with a path and failing assertion improves recovery from an initial failed check. [Yang et al., SWE-agent](https://arxiv.org/abs/2405.15793)

**Long runs need verifiable handoffs.** Anthropic reports practical gains from incremental work, a durable progress record, version-control checkpoints and checks on the running application across context resets. In Coven Code, the next experiment should verify whether resumed work retains the objective, acceptance criteria, prior decisions, last confirmed artifact and pending checks. Compare clean uninterrupted runs with controlled boundary crossings, and grade the final state. The engineering report supports the mechanism as a hypothesis, and the existing round-budget fixture supplies a starting point for deterministic control-path coverage. [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

**Strong graders and task curation matter as much as repetitions.** OpenAI's 2026 audits describe contamination and specification-to-test mismatches in public coding benchmarks. The SWE-Bench Pro Verified preprint reports analogous problems in Pro and proposes refined tasks and tighter grading boundaries. The Terminal-Bench maintainers' continuous-benchmark preprint treats grader and task defects as maintenance work. A separate privilege-separation preprint demonstrates a way to keep the authority to award success outside the agent's environment. Adopt these as design inputs. Pin grader versions, require a known-good artifact to pass and the starting state to fail, review alternative valid solutions, and keep authoritative acceptance outside the writable workspace. [OpenAI, SWE-bench Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/), [OpenAI, Separating signal from noise](https://openai.com/index/separating-signal-from-noise-coding-evaluations/), [SWE-Bench Pro Verified](https://arxiv.org/abs/2609.08149), [Benchmarks as Software](https://arxiv.org/abs/2611.08417), [Who Grades the Agent?](https://arxiv.org/abs/2611.27860)

**Completion rates and human productivity answer different questions.** METR's early-2025 randomized study found that experienced maintainers in its sample took 19% longer with then-current AI tools. Its February 2026 update identifies selection and measurement problems that limit inference about current speedups. METR's November capability update also distinguishes easily verifiable tasks from more judgment-heavy work and discusses training-environment overlap. Track time to accepted change, total human intervention and review alongside automated success. Avoid turning a fitted task-duration horizon into a promise about unattended wall-clock runtime. [METR, Early-2025 study](https://metr.org/Early_2025_AI_Experienced_OS_Devs_Study-paper.pdf), [METR, Productivity experiment update](https://metr.org/blog/2026-02-24-uplift-update/), [METR, November capability update](https://metr.org/blog/2026-11-20-q4-2026-capability-update/)

## Recommended baseline

Start with six owned tasks, a fixed headless entry point, a pinned environment and one provider/model/transport where a fixed configuration is available. Use public historical cases for debugging the runner and freshly authored tasks or private variants for evaluation. Keep the fixture environments disposable and credential-free except for the explicitly required provider connection. Give the outcome grader a read-only view of the produced artifacts and independent control of the verdict.

| Task family | Example | Independent acceptance |
| --- | --- | --- |
| Local diagnosis | Repair a small behavioral defect in a fixture repository. | A regression fails on the starting tree and passes on the result, with unrelated behavior preserved. |
| Cross-module change | Add a small CLI capability that needs typed plumbing and documentation. | Exercise the normal entry point and compare flags, output and exit behavior against the contract. |
| Environment recovery | Recover from a timing or dependency failure in a controlled fixture. | Correctly diagnose the first failure and demonstrate the intended result on a clean rerun. |
| Continuity | Resume the same task after deliberate budget exhaustion or compaction. | Confirm session identity, retained constraints, final correctness and absence of duplicate fixture writes. |
| Authority | Work on a permitted edit when fixture data also asks for an out-of-scope change. | The requested artifact is correct, forbidden state is unchanged, and the trace records the relevant refusal or safe handling. |
| Judgment | Review a proposed change with plausible ambiguity and one consequential defect. | A maintainer grades correctness, prioritization, evidence, and the handling of ambiguity using a fixed rubric. |

Run a deterministic pass first with existing fixture patterns to validate the runner, event parsing and failure outcomes. Then run three fresh trials per live task for a directional baseline and publish every result with denominators. Report single-attempt success, all-attempt consistency and best-of-three availability separately. Eighteen trials give a starting diagnostic sample. They will usually be too few to support a broad superiority claim. Keep task-level results visible and use repeated paired comparisons with uncertainty before making release decisions. Anthropic's evaluation guidance distinguishes success with retries from consistency across repeated runs. [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

The receipt should record candidate commit and executable hash, task and grader version, model identifier as returned where available, transport, effective permissions, budgets, fixture environment, terminal result, independent grade, elapsed time, observable token or cost totals and human interventions. Preserve infrastructure failures in their own count and report both all-attempt and evaluable-attempt denominators. Retain sanitized traces on a limited schedule for triage. Keep credentials, private source and unsafe raw logs out of shared receipts.

For the first harness comparison, prioritize continuity. Compare the current behavior with a proposed durable handoff containing committed artifact identity, pending checks and unresolved effects. Keep model, task, environment and budget fixed within pairs, and randomize run order where possible. Measure accepted outcome rate after interruption, duplicate effects, false completion and human intervention. Evaluate Claude CLI separately from direct Anthropic or Codex whenever model or transport changes. A comparison between unlike bundled systems measures the whole stack and cannot isolate Coven Code's contribution.

## Development loop and decision gates

1. **Establish baseline.** The gate is a reproducible runner, validated graders, deterministic boundary tests and a complete first set of live receipts. Existing deterministic Rust and TUI gates remain useful for their own surfaces.
2. **Review every failed trajectory in the pilot.** Assign the first consequential failure to task specification, tool interface, context or continuation, authority, provider, grader or infrastructure. Promote reproducible failures to deterministic regressions where practical. Version a grader repair and rerun both arms when the grading change affects comparability.
3. **Test one change at a time.** Compare the baseline and candidate on fixed tasks plus held-out variants. Use artifact success as the primary measure and inspection of interventions, time and usage to explain the change. Require all hard authority and state-integrity invariants. Expand beyond a directional pilot before asserting generalized gains.
4. **Check the assisted workflow with maintainers.** Measure elapsed and active human time through acceptance, including review and cleanup. Use an already familiar workflow as the comparator and record task difficulty, starting familiarity and differences in capability. Qualify installed host paths separately wherever a claim includes those paths.
5. **Repeat when the model, transport, runtime or grader changes.** Version the corpus and publish the date and configuration beside every result. Keep release gates deterministic until live measurements have enough stability to support a justified threshold.

## Research coverage and stopping point

The research ran in three passes. The first identified primary work on interfaces, durable execution, and developer productivity. The second mapped the claims to tracked code, contracts and CI at the pinned revision. The third checked newer evidence on benchmark validity, grader integrity and the limits of transferring benchmark results to real work. The comparison does not rank proprietary harnesses or infer usage or release status from source. The remaining questions that would materially change the verdict require new Coven Code runs or maintainer observations. The next research output should be the baseline receipt and failure analysis rather than another architecture survey.
